### P1.6 Partial refresh erases last-good metrics (merge by providerMetricId)
**Files:** `src/server/refresh/refresh-service.ts:289-342`

Current: C3 fix only preserves when `metrics.length === 0 && errors.length > 0`. Partial (some metrics + errors) overwrites entire cache.

Fix: When `result.errors.length > 0 && result.metrics.length > 0` (partial), merge:
1. Start from existing cache `normalized.metrics` as base
2. Build a map of `providerMetricId -> metric` from `result.metrics`
3. For each metric in base: if it exists in result, replace it; if it doesn't, keep the old one
4. Append any new metrics from result not in base
5. Write the merged array as `normalizedForCache`
6. Status stays `"stale"` (already set)

```ts
if (result.errors.length > 0 && result.metrics.length > 0) {
  const existing = storage.providerCache.get(paId)
  if (existing) {
    const resultById = new Map(result.metrics.map(m => [(m as NormalizedMetric).providerMetricId, m]))
    const merged = existing.normalized.metrics.map(oldMetric => {
      const old = oldMetric as NormalizedMetric
      const fresh = resultById.get(old.providerMetricId)
      return fresh ? (fresh as Record<string, unknown>) : oldMetric
    })
    // Add any new metrics not in cache
    for (const [id, m] of resultById) {
      if (!merged.some(mm => (mm as NormalizedMetric).providerMetricId === id)) {
        merged.push(m as Record<string, unknown>)
      }
    }
    normalizedForCache = merged
  }
}
```

### P2.2 checking-session captures stale range
**Files:** `src/client/components/AuthGate.tsx:31-52`

With `key={profileId}` (P1.4), the component remounts on profile change but NOT on range change. The session-check effect captures `range` from the initial render. If range changes before session check resolves, the payload is for the old range.

Fix: Change effect deps to `[profileId, range]`. On range change: abort in-flight session check, reset to `"checking-session"`, re-fetch with new range. The abort cleanup already handles the stale response.

Note: this means range switches on the login screen re-trigger the session check. This is correct behavior - the initial payload should match the current range.

